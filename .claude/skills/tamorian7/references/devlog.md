# log — 実録の型

**声・見出しの形は `kuroko-voice.md` を先に読む。**
以下の4セクションは「何を集めるか」の下ごしらえとしては使えるが、
**見出しとして本文にそのまま出さない**（2026-08-31、「壁1:」のような
番号見出しが「エントリーシートみたい」と指摘された）。

`src/content/log/<YYYY-MM-DD>.md`。日付で固定し、**書いたら基本いじらない**。

log は溜め場ではなく **吐き出し先**。works の作業場に溜まったものをここへ切り出す。

## 4つのセクション

1. **なぜやったか** — 1〜2文。判断のため / 予習のため、など動機
2. **実測でわかったこと** — 箇条書き。数字には**必ず単位と測定条件**
3. **実装で刺さった罠** — 番号付き。**自分のバグを必ず含める**。
   「ライブラリが悪かった」だけで終わる記事は薄い
4. **未確定のまま残したこと** — n数と、**なぜ結論にしなかったか**

一般論に昇格する部分は garden ノートへ切り出してリンクする。

> 手本: `src/content/log/2026-07-26.md`(Fugu の裏トークン実測)。
> 3 の「自分のバグ」は当事者にしか書けず、他所からコピーできない価値になる。
> 4 は誠実さの担保であると同時に、後日の再検証タスクとして機能する。

## 原料

事後に「今日のこと書いて」と頼んでも、**成功した最終形しか復元できない**。

- `git log`(wip コミット込み。失敗中の状態も症状をメッセージに書いて残す)
- `scratch/<YYYY-MM-DD>.md`(作業中の転びを時刻付きで箇条書き)

## 足りないときは書かずに問う

3 と 4 が埋まらないなら勝手に埋めない。
「本当に何も転ばなかったか」「その数字は何回測ったか」を聞き返す。
