- 19:50 **px4_drv を除外。** 対応デバイス一覧に無印 Q3PE が無いのと、

### ビルドで踏んだもの(全部 kernel が新しいせい)

- `make` が何も作らない。`obj-m` が空だった。**Makefile が bash 構文
  (`$(shell eval source dkms.conf)` と配列展開)なのに、make の `$(shell)` は
  `/bin/sh` = dash。**`SHELL=/bin/bash` で解決
- `media/dvb_math.h` が無い。headers パッケージに含まれない。ただし
  `intlog10` は `Module.symvers` に**今もエクスポートされている**ので、宣言だけ自前で補った
- `i2c_driver.probe` の第2引数が 6.3 で削除。6ファイル
- `i2c_driver.remove` が 6.1 で `int` → `void`。4関数
- `objtool: unannotated intra-function call`。**リポジトリ独自の `-O3 -Os`** が原因。
  カーネル既定に戻したら消えた
- `pci_set_dma_mask` (5.18廃止) → `dma_set_mask`、`strlcpy` (6.8削除) → `strscpy`
- `pci_alloc_consistent` は **PT3 用ファイル**。持っていないので dkms.conf から外した
- 20:02 8本のノードが出た。`/dev/pxq3pe_drv00t` 〜 `07s`。
  **地上波と衛星が交互**(偶数=t、奇数=s)。`device_create` の書式
  `"%s%x%x%c" ... i & 1 ? 's':'t'` から読めるとおり
- 20:05 `recpt1` をビルド。**リポジトリに `pt1_ioctl.h` が入っていない**ので
  ドライバの `enum eUserCommand` と `struct sFREQUENCY` から生成した

### ここから半日ハマる

- 20:10 物理チャンネル13〜52を掃引、全滅。**「電波が来ていない」と結論した。これが誤り**
- 20:20 ログを読み直したら、**読み出しが1回も実行されていない。**
  `tc90522_i2c_r_1` は2メッセージ転送なのに、書き込みの直後で止まっている
- 20:25 `pxq3pe_i2c_xfer` が **`return i`**。`for (i = 0; i < sz && ret; i++, msg++)` で
  **失敗しても i は加算されてから抜ける**。1メッセージ書き込みは `== 1` で成否を見るので、
  **失敗しても成功に見えていた。** 2メッセージの読み出しだけが `== 2` で正しく検出していた
- 20:28 `return ret ? i : -EIO` に直したら **probe が落ちるようになった。**
  つまり**ずっと失敗していた**。直したのではなく、見えるようにしただけ
- 20:30 `pxq3pe_w ABORT fifo_stat=0000800b`。FIFO_STAT の下位5ビットが
  `0x0b`、期待は `0x10`。I2C コントローラが詰まっている
- 20:35 **ガードがリセットより前にあった。**
  ```c
  if ((readl(FIFO_STAT) & 0x1F) != 0x10 || ...) return false;
  writel(0, CTL_STAT);   /* ← 掃除はこの後 */
  ```
  一度汚れると掃除する処理に到達できない。**掃引の結論を取り消し。**
  最初の1回が失敗した時点で、残り39チャンネルは必ず失敗する運命だった。
  **掃引が示していたのは1件目だけ**

### 効かなかったもの(記録しておく価値がある)

- `writel(0, CTL_STAT)` をガードの前に移動 → `ABORT after reset`。**値が動かない**
- **PCI ファンクションリセット(`pm` / `bus`)** → **全レジスタが1ビットも変わらない。**
  「Q3PE は温かい再起動でリセットされない」という既知の癖の正体はこれ。
  回避策ではなくハードの仕様
- `hw_init` 冒頭の設定書き込み(`0x904`/`0x900`/`0x890`)を手で再現 → 動かない
- `FIFO_DATA` を16回読む → `0x0a` のまま、データも常に 0。**吸い出せる種類の詰まりではない**
  - これは本人の「FIFO のカウンタなら読んだら減るのでは」という指摘から試した。
    外れたが、**測定自体を疑う視点は正しかった**(こちらは peek が破壊的でないかを
    先に確かめるべきだった)

### 残った問題

- 走査し直したが **13〜52ch すべて C/N が `nan`**。今度は掃引が信頼できる
  (失敗しても刺さらない)ので、**本当に電波が来ていない**
- BS(101ch、LNB 15V も試行)も失敗。TSID が読めない
- **ケースが干渉して、カードの片方の端子にしかケーブルが挿さらない。**
  短いのではなく**細い**ケーブルが要る(2.5C・外径4mm・L型・F型ネジ式)
- **ブラケット紛失でカードは自重のみで載っている。** ただし `LnkSta` は
  `x1 @ 2.5GT/s`・エラーカウンタ0で電気的には健全。硬い同軸だとカードを浮かせる方が心配
- **内蔵 B-CAS リーダーは使えない。** `SET_BCAS_COMMAND` / `GET_BCAS_COMMAND` が
  `return 0` のスタブ。USB のカードリーダーが要る

### 未解決のまま残すこと

- **SW_CTL のどのビットがリセットかは未同定。** 全ビット立てて戻すという乱暴な手のまま。
  `orig|1` だけでは効かなかったので bit0 ではない
- **そもそもなぜ FIFO が汚れるのか分かっていない。** probe の途中で `0x10` → `0x0a` に
  変わる。末尾の `tc90522_lnb()` が最初の「読み出し」を発行するので疑っているが、
  dyndbg を probe より前に有効化できておらず、**その瞬間を撮れていない**
- 対症療法である自覚はある
