## 続き: 本人は家にいなかった → 20:03 は機械側で確定

叩くのを止めて、動かさずコードだけ読んだ。

- 1276行 `writel(0, ... DMA_ADR_HI)` で上位32bitを0固定。だが 1511-1512 で
  `dma_set_mask`/`dma_set_coherent_mask` に `DMA_BIT_MASK(32)` を通している。
  `||` の連鎖は成功時 0 なので**全部実行される**(読みにくいだけで正しい)。**無罪**
- `sBufSize = PKT_BYTES*100<<9` に対し流し込むのは `PKT_BUFLEN = PKT_BYTES*312`。
  桁が違うのでリングの溢れもない。**無罪**
- `tBuf[PKT_BUFLEN]` への `memcpy` は寸法チェックが後ろだが、idx は必ず
  PKT_BYTES の倍数で PKT_BUFLEN 丁度で0に戻る。**溢れない**

### 見つけた不具合1: DMA が止まらない (pxq3pe_dtv.c:1289)

```c
for (i = 0; i < card->adapn; i++)
    if (!card->dma.ON[port] || (i2cadr != i && (i & 4) == (i2cadr & 4) && card->dma.ON[port]))
        return;
```

「同じポートの他のチューナーがまだ使用中なら止めない」のつもりだが、見ているのが
**ポート単位の `dma.ON[port]`** で、その兄弟が実際に使用中かを見ていない。
止めに来た時点で `dma.ON[port]` は真なので、**同じポートの別 adap が1つでもあれば
必ず early return する**。つまり `cancel_dma` に到達しない。

→ 一度録ったら **recpt1 が終わってもカードは DMA を続け、IRQ も上がり続ける**。
掃引で12回連続で叩いたのは、この状態を12回重ねたことになる。

### 見つけた不具合2: IRQ 登録がバッファ確保より先 (1583 → 1587)

`request_irq(..., IRQF_SHARED, ...)` の**後**に `dma_alloc_attrs`。
その隙に共有IRQが上がると `card->dma.dat` が NULL のままハンドラが走る。
`intstat & 0b1111` のガードは通るので、ビットが立っていれば `tbuf[i]` を
**NULL 参照**する。載せ直しを繰り返している今の状況では踏みうる。

### なぜ何も残らないか

- `/proc/cmdline` に `intel_iommu=on` なし
- 前ブートのカーネルログに `DMAR-IR`(割り込みリマップ)はあるが
  **`Virtualization Technology for Directed I/O` の行がない = DMA変換は無効**
- → 不正 DMA は弾かれも記録もされず物理メモリを直に壊す。panic も pstore も空、で辻褄が合う

## 00:30 諦めている一点まで詰めた

### 待っているのはレジスタ 0x80 のビット3

`tc90522_chk_lock` (pxq3pe_dtv.c:428) の地上波側:

```c
(tc90522_i2c_r_1(fe, 0x80, &d0), (d0 & 8) == 0)   &&   /* ここで止まる */
(tc90522_i2c_r_1(fe, 0xB0, &d1), (d1 & 0xF) > 7);
```

実測は `ae` / `af` / `2e`。**どれも `& 8` が 1** なので第1条件が通らず、
0xB0 は一度も読まれない。499回の読み出しが全部同じレジスタだったのはこのため。

### 書き込みが落ちるのは毎回ではない

- ある実行: 書き込み509回 / FAIL **0**、読み出し499回すべて ok=1
- 別の実行: 書き込み FAIL **16回**（`j=1000`、完了ビット 0x400000 が立たない）

**走るたび変わる。** I2C の詰まりは起きるが、ロックしない主因ではない。
詰まらない実行でもロックしていない。

### DVB 版との差: `retryov` を見ていない

同じ作者の独立実装 `drivers/media/dvb-frontends/tc90522.c:171`:

```c
retryov = data[0] & 0b10000000 ? true : false;   /* 0x80 bit7 */
lock0   = data[0] & 0b00001000 ? false : true;
lock1   = data[1] & 0b00001000 ? true : false;
if (lock0 && lock1) → ロック
if (retryov) break;
```

- `0xB0` の判定は `(d1 & 0xF) > 7` と `d1 & 0x08` で**等価**。差ではない
- **差は `retryov`(0x80 のビット7)を見ているかどうか**。chardev 版は見ていない
- 実測 `ae` = `1010 1110` は **ビット7が立っている** =
  **復調器自身が「掴もうとして諦めた」と言っている**

これは待ち時間が延びるだけのバグで、ロックしない原因そのものではない。
ただし**復調器の自己申告が取れた**意味は大きい。

### いま言えること

I2C は通る。チューナーへの書き込みも通る。復調器も生きた値を返す。
そのうえで**復調器が「ここには何も無い」と言っている**。残る可能性は2つ。

1. このカードに RF が来ていない
2. チューナーが目的の周波数に乗っていない（プログラミングが違う）

**ドライバはチューナーの PLL ロックを一度も確認していない。** これを見れば1と2が割れる。
`nm131_r` はあるのでレジスタは読めるが、どのビットがロックかはデータシート待ち。

地上波チューナーの周波数設定は 1029行 `nm131_w(fe, 0x1BC, (ddfs_lut << 14) / rf, 4)` 付近。
整数除算があり、ここが微妙にずれていても「近いが掴めない」になる。
**Windows の .sys で確かめたいのはまさにこの並び。**
(629-710行の分数N演算は 1GHz 超の閾値なので衛星側。地上波ではない)

## 01:0x Codex に診断を委託 → こちらの見立てが2つ潰れた

### 潰されたもの

1. **「retryov が立っている = 復調器が諦めた」は言い過ぎ。**
   `retryov` はこのリポジトリの変数名にすぎず、mainline はその名を使わず
   px4_drv は bit7 を判定に使っていない。**実測 `0x2e` は bit7 が無いのに失敗している**。
   bit7 だけを根拠に断定してはいけない
   （0x80 のビット: bits3/2 = sync/viterbi 無し、bit1 = 最終ロック無し）
2. **「chardev 版と DVB 版のシーケンス差が本命」は外れ。**
   probe 時の TC90522 `B0-B8, 03, 1D, 1F, 0E, 0F, 75`、NM120/131 の既定値、
   tune 時の AGC 停止→NM131 設定→AGC 再開→`71/72` は**実質同じ**。
   差はエラー処理だけ。**DVB 版は独立した正解実装ではなく、同じ算術を共有している**
3. **`nm131_w(fe, 0x1BC, (ddfs_lut << 14) / rf, 4)` の整数除算も外れ。**
   `ddfs_lut` は定数ゼロ(942行)なので式は常に 0。Hz/kHz の取り違えも無く、
   ch番号→539MHz の式も ch24 で正しい

### 新しい容疑（Codex 発）

- **1034行の符号なしアンダーフロー**
  `((864 * (clk_off_f >> 5) - 1308983296) / 216000 ...)`
  `clk_off_f` が `u32` なので減算が符号なしで回り込む。ch24 では
  実際に書かれるのは `0x000038c3`、符号付きのつもりなら `0xffffeb13`。
  レジスタ仕様が無いのでどちらが正しいかは不明
- **985行、`xo` の反復更新**
  `0x21 & 3` が 2 か 3 なら再計算ループごとに `xo` を倍/半分にするので
  2周目には 4倍/¼ になる。**`0x21` の下位2bit は実測すれば分かる = 次の実験**

### 一致した点

Codex も優先順位を「**RF 経路・レベル** → NM131 の PLL/IF 成立 → TC90522 の
ボード固有初期化」と置いた。**独立に追って同じ順番になった**。

TC90522 の初期化列は非公開で、mainline 自身が「PCI ブリッジ側が事前に正しく
設定する前提」と書いている。NMI120 のデータシートにレジスタマップは無い。
TS 出力の設定ミスなら「ロックするが TS が出ない」になるはずで、
0x80 段階で失敗している今の症状の原因としては優先度が低い。

### ch24 の実測計算値（Codex による）

    lofreq 539143857 / v14 4313144 / v14/216000 = 19
    clk_off_f 5635880 / rf 17218 / 0x230 = 0x000baa4e / 0x1BC = 0x00000000

## 06:4x Windows ドライバを入手した。LLM PC は要らなかった

### まず自分のミスで一晩無駄にしていた

    RuntimeError: rc=2: psrun.sh: 10: set: Illegal option -o pipefail

`psrun.sh` は bash 前提なのに、キューのコマンドに `sh psrun.sh` と書いた。

しかも仕事が failed に移った結果 `wake.json` が「仕事が無い」と判断し、
**起こす要求自体が出なくなっていた**(仕事が消えると起こす理由も消える)。
`psrun.sh` は実行属性付きなので直接呼べばよい。積み直した。

### 結局ダウンロードで済んだ

    http://plex-net.co.jp/plex/px-q3pe/PX_Q3PE_BDA_DRIVER.zip

→ `~/px-q3pe-bda/` に展開。`HDTV_PX_Q3PE_BDA.sys`(64bit, 267KB)。
`.inf` が `PCI\VEN_188B&DEV_5220&SUBSYS_00020B06&REV_01` を宣言していて**実機と完全一致**。
**アトリエの PC を起こす必要は最初から無かった。** 電気代のゲートを気にして
一晩待つ前に、配布物を探すべきだった。

### 定数で対応が取れる

Linux 側の特徴的な定数をバイト列で検索したら直撃した。

    1308983296 (0x4E058000)  → .sys の 0x1e30 に1箇所
    864        (0x360)       → 0x1e29 = その7バイト手前
    0x11C0E520 (DMA_CTL)     → 2箇所
    0x3200C8   (hw_init)     → 1箇所

**同じハードを同じ手順で叩いている。** 逆アセンブルすれば1対1で比較できる。

### 分かったこと1: Codex の「符号付きのつもりでは」は外れ

```asm
shr  r8d, 0x5          ; 論理シフト
imul r8d, r8d, 0x360   ; * 864
sub  r8d, 0x4e058000
mul  r8d               ; 符号なし乗算。0x36b06e71 は /216000 のマジック
shr  r8d, 1            ; 論理シフト
shr  r8d, 0x11
```

`sar` でも `imul`(乗算側) でもない。**Windows も全部符号なし。**
アンダーフローは意図された挙動で、Linux 版は忠実。ここは無罪。

### 分かったこと2: マスクが違う(直した)

    Linux    ... & 0xFFFFFFF0 | 3
    Windows  ... & 0xFE00FFF3 | 3     ← ビット16-24 も落とす

Windows は**両系統とも**このマスク。分岐に関係なく必ずやる処理なので合わせた(dc801ac)。
直後が `mov edx,0x210` → 書き込み、次が `0x104`。こちらの
`nm131_w(0x210)` → `nm131_r(0x104)` と並びが一致するので**対応は確実**。

### 分かったこと3: Windows には第2系統がある(こちらには無い)

```asm
test edi, edi
je   → 第2系統          ; edi == 0
cmp  edi, 0xd
je   → 第2系統          ; edi == 13  ← ISDB-T フルセグのセグメント数
                        ; それ以外 → 第1系統
第1系統内: cmp edi,5 / cmp edi,7 → or r8d, 0x1390000
```

    第1系統  864 / 0x4E058000
    第2系統  858 / 0x4F41E800

**Linux には 858 も 0x4F41E800 も 0x1390000 も 0xFE00FFF3 も無い**(grep で確認)。
3通りある処理を1通りしか実装していない。

### 試した結果: どちらも 0/50

- マスクだけ合わせた版 → 0/50。0x80 は `ca`(bit3 立ったまま)
- 858 系統に切り替えた版 → 0/50
- **根拠のない 858 は戻した。** `edi` が何かを同定できていないのに固定するのは誤り

### 次

**手法は確立した。** 定数で当たりを付けて逆アセンブルすれば、tune 経路の全体を
1対1で比較できる。0x210 は多数ある書き込みの1つにすぎない。
次は単発のレジスタではなく**書き込み列そのものを頭から突き合わせる**。
`nm131_w`/`nm131_r` に相当する呼び出し(`call 0x1168` / `call 0xedc`)を辿れば、
Windows が実際に投げるレジスタと値の並びが全部取れる。

## 07:0x 書き込み列を丸ごと突き合わせた → Linux が大量に書いていない

`call 0x1168` = nm131 書き込み、`call 0xedc` = 読み出し。
直前の `mov edx,<reg>` と `mov r8d,<val>` を拾って列を復元した。

### Windows の列（★ = Linux 側に無い）

    ★ 0x1C0 = 0x358CFFFF
    ★ 0x130 = 0x200
      0x164 = 0x600
    ★ 0x20C = 0x100
      0x230 / 0x250=0x4 / 0x27C=0x1010 / 0x1BC
    ★ 0x1C8 = 0x8000   ┐ edi==13 のときだけ
    ★ 0x1CC = 0x8000   │
    ★ 0x1D0 = 0x8000   │
    ★ 0x110 = edi-11   ┘ (13-11 = 2)
    ★ 0x26C
    ★ 0x1CC = 0x8079   ┐ それ以外の分岐
    ★ 0x1D0 = 0x8079   │
    ★ 0x110 = 0x4C52   │
    ★ 0x26C = 0x2      │
    ★ 0x270 = 0x6      ┘
      0x21C(R/W を数回) / 0x234(R,R)
    ★ 0x148 = 0x1001
    ★ 0x200 (R して W)
      0x210 / 0x104 / 0x328

### 現物での裏取り

```asm
1997: cmp  edi, 0xd        ; 13 = ISDB-T フルセグ
199a: jne  0x1a20          ; 13 でなければブロックごと飛ばす
19a0: mov  r8d, 0x8000
19a6: call 0x1168          ; 0x1C8 = 0x8000
      ... 0x1CC, 0x1D0 も 0x8000
19d1: lea  r8d, [rdi-0xb]  ; edi-11 = 2
19dd: call 0x1168          ; 0x110 = 2
```

**ISDB-T のときだけ走る設定ブロックが丸ごとあり、Linux はどちらの分岐も実装していない。**
`edi` は 0/5/7/13 を取り、`edi-11` としても使われる。**モード/帯域の指定**とみて
ほぼ間違いない。13 がフルセグ。

### これが本命だと思う理由

Linux が持っているのは `0x164/0x230/0x250/0x27C/0x1BC/0x21C/0x234/0x210/0x104/0x328` で、
**列の頭(0x1C0/0x130/0x20C)と中盤のブロック(0x1C8/0x1CC/0x1D0/0x110/0x26C/0x270)と
0x148/0x200 が丸ごと欠けている**。フィルタ/帯域まわりの設定が一度も書かれていない
なら、PLL が乗っても復調器が掴めないのは筋が通る。

### 注意

値が空欄のものは即値ではなく計算結果。`mov r8d,imm` を拾う機械的な抽出なので、
**定数のものは確かだが、計算されるものは呼び出し元を追う必要がある**。

### 次

定数で書けるものから移植して試す。
`0x1C0=0x358CFFFF` / `0x130=0x200` / `0x20C=0x100` / `0x148=0x1001` と、
ISDB-T 分岐の `0x1C8=0x1CC=0x1D0=0x8000` / `0x110=2`。

## 09-07 11:0x I2C の失敗は「チューナー宛の複数バイト書き込み」に集中していた

### SW_CTL(0x948) の正体が分かった（README の未解決事項）

Windows(.text+0x25b2d..0x25b88):

```asm
or  ebx,0x20        ← ビット5 だけ立てる
write SW_CTL / 待つ(0x32)
and ebx,0xffffffdf  ← 下ろす
write SW_CTL / また待つ
FIFO_STAT を読み直して (stat & 0x1F)==0x10 でなければ失敗扱い
```

**リセットはビット5 のパルス。** 全ビット叩きではなかった。
元の実装は32ビット全部を立てて戻し、しかも待ちが無い。直した。
ただし**これでは症状は変わらなかった**（後述のとおり復帰処理は呼ばれていない）。

### 完了ビットが読みと書きで食い違っていた

    書き込み  if (readl(CTL_STAT) & 0x400000) break;   ← ビット6
    Windows   shr ecx,0x10 / test cl,cl / jns          ← ビット7 = 0x800000
    読み出し  i2cStat & 0x80                           ← ビット7。Windows と同じ

書き込みだけが違うビットを見ていた。0x800000 に合わせた。
**失敗数が変わらなかったので、成功している書き込みでは 0x800000 も立つ**
（=この変更は安全側）。ただし症状は変わらない。

### 誤報しかけたもの

`0x944` への書き込みが Windows にあって Linux に無い、と思ったが
`PXQ3PE_I2C_ADR = 0x944` で Linux も書いていた。**定義名で検索する前に
オフセットだけ見て判断しかけた。**

### 失敗の内訳（ここが本題）

3通りの変更を試して**失敗数がきっかり125で不動**。内訳を見たら:

    86回  slvadr 00 wdat fe len 8 mode 01   ← nm131(コマンドは 0xFE 始まり)
    29回  slvadr 00 wdat fe len 4 mode 01   ← 同上
     5回  slvadr 80 wdat 80 len 1 mode 02
     5回  slvadr 00 wdat 23 len 2 mode 01

    70回  ctl_stat=00100880   下位0x0880 = こちらが書いたコマンド、バイト2が 0x10
    20回  ctl_stat=00100480
    10回  ctl_stat=00700880 (j=19)

**115/125 がチューナー宛の 4/8 バイト書き込み。** 復調器宛の 1〜2 バイトは通る。
**長い書き込みだけが通らない。** バイト2が 0x10 のまま進まない。

### まだ潰せていない差

Windows の FIFO 充填(.text+0x25c48..0x25ca4)は
**1ワード書くたびに待ち(call 0x2715c, ecx=0x32)を入れている**。
Linux は最初の16バイト分のループで `msleep(0)`。
バイトの組み立て順は等価だった(b[-2]が LSB で、r13 が wdat+2 始まりならリトルエンディアン)。

### 次

長い書き込みだけが落ちる理由。FIFO の充填と CTL_STAT へのコマンド発行の
順序・タイミングを Windows と1対1で突き合わせる。
`0x944`/`0x94c`/`0x954` のうち **Linux が知らない 0x94c と 0x954** も要確認。
