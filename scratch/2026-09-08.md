## ドライバが自動ロードされない（重大・見つけて直した）

`modinfo` で `.ko` に **alias が1つも無い**。`modules.alias` にも該当0行。
**このまま再起動したらチューナーが載らず、録画システムが黙って死んでいた。**

ソースには `MODULE_DEVICE_TABLE(pci, pxq3pe_id_table)` が **ある**（28行目）。
depmod も走っている（modules.alias が .ko より3秒新しい）。
**ビルドの過程で落ちている。** Makefile の `ldflags-y += -s` が怪しいが未確認。

    rmmod 後             モジュール0 / デバイス0
    systemd-modules-load モジュール2 / デバイス8

## 復号しながら録画したときの余裕を測った

結論: **復号はタダ。詰まるのは既存の読み出し経路。**

### MULTI2 の速度（カード無しでも測れる）

鍵が正しいかは処理量に影響しないので、libarib25 を建てて `create_multi2()` を
直接叩いて測った。i7-6700 / 4C8T。

    1コアあたり 2,887 Mbps (TS換算)
    地上波1本(17Mbps) = 0.6% / 8本(136Mbps) = 1コアの 4.7%

**前提を検証してから採用した**（空のループは常に通る）:
`set_*` と `decrypt` の戻り値が全部0、184バイト中183バイトが変化、
encrypt→decrypt で元に戻る。→ 実装は本当に動いている。

なお **AVX2 命令は0個**（`objdump` で確認）。SIMD 版(multi2_ymm.h)は
コンパイルされておらず、これはスカラー実装の数字。有効化すればさらに速い。

### B-CAS カードを叩く頻度（実録画から実測）

    ECM の送出      10.00 回/秒   （冗長に何度も送られてくる）
    中身が変わる     0.50 回/秒   ← カードを叩くのはここだけ
    鍵の更新間隔     2.0 秒に1回

libarib25 は ECM の中身が変わったときだけカードに問い合わせる。
**8本同時でも 4回/秒**。カードの応答が数十msでも十分間に合う。

### 本当のボトルネック: recpt1 が空回りしている

録画1本を20秒流して、プロセス別に CPU を測った:

    recpt1      コア 1.023 本   ← これ
    Mirakurun   コア 0.028 本

**15Mbps(1.9MB/s)を運ぶのにコア1本は異常。** ドライバを読んで原因判明:

`pxq3pe_read` (1503行) は **待たない**。データが溜まっていなければ 1540行で
`rlen = 0` にして即座に0を返す。待ちキューが無い。
さらに **1507行で毎回 `kzalloc(rlen, GFP_ATOMIC)` してゼロ埋め**してから、
読むものが無いと分かって 1541行で捨てている。

recpt1 側は `MAX_READ_SIZE = 188*87 = 16,356` バイトを、失敗しても間を空けずに
読み続ける（recpt1.c 863/888行）。15.5Mbps なら 16KB は 8.4ms に1回しか
埋まらないので、その間ずっと **16KBの kzalloc+ゼロ埋め+kfree** を回している。

### 8チューナー同時録画の見込み

    いま        8本 × 1.02 コア = 8.2 コア  > 8論理コア → 飽和
    復号を足す  8本 × 0.006 コア = 0.05 コア → 誤差
    読み出しを直せば  8本でも余裕

**「復号する余裕があるか」の答えは「余裕はあるが、別の理由で既に食われている」。**

直し方: 待ちキューを足して read をブロックさせる。最低限でも
kzalloc をデータ有無の判定より後ろへ移すだけで大半が消える。
再ビルドが要るので、b25 対応と PCI alias の件と一緒にやる。

## 3点まとめて直した

### 1. read の空回りを止めた（1.023 → 0.018 コア）

`kzalloc` をデータ有無の判定より後ろへ移し、足りないときは
`usleep_range(1000,2000)` して戻すようにした。待ちキューが本筋だが、
**動いているものを壊す危険が小さい方**を選んだ。recpt1 は 0 を EOF と
見ずに continue するので、ドライバ側で待たせれば安全に止まる（確認済み）。

ロック内で `sBufByteCnt` を取り直すようにもした（元は判定がロック外）。

**取りこぼしが出ていないことを必ず確認する。** 待たせた分バッファが溢れうる:

    1本  20秒  224,683パケット  同期エラー0  連続性の跳び0
    4本  25秒  各20〜30万パケット  4本とも 同期エラー0 / 跳び0

### 2. PCI エイリアスが消えていた原因を特定した

**`ldflags-y += -s`。** modpost は `__mod_pci__..._device_table` という
**シンボル**を見てエイリアスを作るが、`-s` がリンク時にシンボルを落とすので
何も作られない。外したら入った:

    pci:v0000188Bd00005220sv00000B06sd00000002bc*sc*i*

`modules.alias` にも載ったので、起動時に自動ロードされる。
`/etc/modules-load.d/pxq3pe.conf` は保険として残す。

### 3. b25 対応の recpt1 を別に建てた

`~/recpt1-b25/recpt1`。**現役の `~/ptx-q3pe/apps/cdev/recpt1/recpt1` は無傷**
（8月19日のまま、b25 の記載なし）。コンテナに渡しているのはそちらなので、
しくじっても録画は止まらない。libarib25 は `/usr/local` に導入済み。

カード無しで `--b25` を付けると:

    Cannot start b25 decoder
    Fall back to encrypted recording

**暗号化のまま録画を続ける。** カードが飛んでも録画が止まらない良い挙動。

### 8本同時録画の見込み（実測から）

    4本同時   コア 0.462 本（1本 0.116）

    復号を足す  8本で +0.05 コア
    →  1割強で収まる。B-CAS を入れても重くならない
