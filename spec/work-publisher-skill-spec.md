# work-publisher スキル仕様書

## 概要

作品が完成したとき、Works Portal への登録・公開までを型化する Claude 用ユーザースキル。「提案→承認→反映」の二段階で動き、承認なしに公開しない。あわせて制作で得た知見をブログ素材として `drafts/` に残し、翌日のデイリーブログに繋ぐ。Claude Code(ポータルのリポジトリがある環境)での使用を主想定とする。

## 発動条件 (description に書くトリガー)

- ユーザーが「これ公開して」「ポータルに登録して」「works に追加」と言ったとき
- 明示依頼がなくても、作品(アプリ・ツール・ライブラリ)の実装が一区切りつき、動作確認まで済んだ文脈では「ポータルに登録しますか?」と提案してよい(提案止まり・読み取りのみなので自発発動しても安全)
- 「まだ登録しない」と言われたら、その作品を `status: planned` または `wip` として登録する提案に切り替える

## 手順

### Step 1: エントリ案の生成(読み取りのみ)

作品のコード・README・会話文脈から以下を推定して提示する:

- `title` / `emoji` / `description`(2 行)
- `category` と `tags`(既存 works.json の語彙に揃える。新語彙は理由を添える)
- サブドメイン案(短く・既存と衝突しないこと。`works.json` を確認して検証)
- `status`(published / wip / planned)
- 配信形態: 静的ファイルのみか、サーバープロセスが要るか

提示フォーマットは JSON エントリそのもの + サブドメイン案 + 「知見メモ案(drafts 行き)」の 3 点セット。

### Step 2: 承認待ち

ユーザーの明示的な承認(「OK」「それで」等)があるまで一切のファイル変更を行わない。修正指示があればエントリ案を直して再提示する。

### Step 3: 反映(承認後)

1. `works.json` にエントリを追記し、`works.schema.json` で検証。失敗したら反映を中止して差分を戻す
2. 公開する場合(`status: published`):
   - 作品ファイルを `/srv/works/<id>/` に配置(またはリポジトリの所定ディレクトリ)
   - `Caddyfile` にホストブロックを追記、cloudflared の `config.yml` にホスト名を追記
   - `deploy.sh` を実行
   - 公開 URL に HTTP リクエストして 200 を確認。失敗したら原因を報告(自動ロールバックまではしない)
3. 知見メモを `drafts/YYYY-MM-DD-<id>.md` として保存(ハマった点・工夫・次への学びを 5〜10 行)
4. 結果報告: 公開 URL、変更したファイル一覧、drafts に残したメモ

## 制約・注意

- サーバープロセスが必要な作品(Python バックエンド等)は、systemd ユニットの追加が必要になる。v1 のスキルでは「静的配信できる作品」のみ全自動対象とし、プロセス型は手順を提示して人間の作業に委ねる
- サブドメインは一度公開したら変えない前提で慎重に決める(リンク切れ防止)
- works.json の直接編集以外の方法(スクリプト経由等)が用意されたらそちらを優先する
