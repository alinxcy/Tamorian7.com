# Knowledge Garden — 個人ナレッジベース(公開デジタルガーデン)仕様書 (v2)

> このドキュメントは旧 `works-portal-spec.md` (v1) を**置き換える**。
> 壁打ちの結果、主役が「作品カタログ」から「自分用の知識ベース」へ、
> 配信が「自宅 Raspberry Pi」から「クラウド静的ホスト」へ変わった。
> さらに掘った結果、**理想の肝は「情報設計(探せる・繋がる)」**であり、
> コンテンツは**「育てる常緑ノート」と「流すログ」の2本立て**だと定まった。
> 判断の背景は各セクションの引用ブロックに残す。

## 概要

AI と何かを作る過程で得た知見・ノウハウを **自分用に貯めていく知識ベース**。
主目的は自分のためだが、見られても構わないので **公開デジタルガーデン** として
出す。静的サイトとしてビルドし、git push でクラウドに自動デプロイして完結させる。
コンテンツ追加は「会話で得た知見を Claude が Markdown として追記・commit する」運用
を前提とし、人間が管理画面を触る仕組みは作らない。参考:
[TNKS1407](https://tnks1407.com/)(Astro + Cloudflare Pages 構成)。

コンテンツは2種類を**分けて**持つ:

- **常緑ノート(garden)** — トピック単位。**後から何度も育て、ノート同士を相互
  リンクで繋ぐ**。知識ベースの主役。日付は脇役
- **ログ(stream)** — 日付順に流す作業ログ・日記。書いたら基本いじらない

そして **このサイトが参考元を超えるべき唯一の軸は「情報設計」** ——
検索・タグ・目次・ノート間リンクで **「探せる・繋がる」** を核に据える。

> **なぜこの形か(壁打ちの結論):** 参考元は「できは良いが理想ではない」。
> 物足りなさの正体は *情報設計が弱く探しにくい* こと(ブログ的な点そのものは不満
> ではない)。そして理想は *流れるログと育てる常緑ノートの両立*。よって本プロジェクト
> は「2本立てのコンテンツ」を「強い情報設計」で束ねることを最優先の差別化点とする。

## システム構成

```
[閲覧者 / 自分]
     │ https
     ▼
[クラウド静的ホスト]           [GitHub リポジトリ]
  Cloudflare Pages       ◀── git push ──  ・常緑ノート  src/content/garden/*.md
  もしくは GitHub Pages       (自動ビルド)  ・ログ        src/content/log/*.md
     ▲                                     ・Astro プロジェクト + frontmatter スキーマ
     │ 静的配信(HTML/CSS/JS)
     ├─ Pagefind 全文検索(クライアント側・バックエンド不要)
     └─ タグ / 目次 / ノート間リンク・バックリンク

[Claude (claude.ai / Claude Code)]
  会話で得た知見 → 常緑ノート or ログを書き出し → commit / push
```

- **入口は git push のみ。** ホストが検知して自動ビルド・デプロイ
- サーバープロセス・常駐・ポート開放なし。落ちない・無料・管理不要
- 検索もクライアント側で完結。動的バックエンドを持たない

> **なぜ自宅 Pi をやめたか:** 憧れた完成度は「自宅サーバーで頑張った結果」ではなく、
> Astro をクラウド静的ホストにポン置きした結果だった。Pi 配信は停電・回線断で落ち、
> 運用も重い。静的ホストなら SLA を気にせずコストゼロで理想に届く。ホスト先は
> こだわりが無いため実装時に選ぶ(推奨は Cloudflare Pages、未確定事項参照)。

## コンポーネント仕様

### 1. コンテンツ(2つの Content Collection)

Astro の Content Collections で **`garden`(常緑ノート)と `log`(ログ)** の2つを
定義し、それぞれ frontmatter を **zod スキーマで検証**する。壊れた frontmatter は
ビルドが失敗して弾かれる(自前 JSON スキーマ検証はこれで代替)。

**garden(常緑ノート)** — `src/content/garden/<slug>.md`

```yaml
title: ノートのタイトル
tags: [astro, cloudflare]
updated: 2026-07-18      # 最終更新(育てる前提なので created より updated を主に)
created: 2026-07-18      # 任意
summary: 一覧やOGに出す1〜2行(任意)
kind: note               # note | work   (省略時 note)
# --- kind: work のとき使う追加フィールド ---
status: published        # published | wip | planned
url: https://...         # 公開作品URL(任意)
repo: https://...        # リポジトリ(任意)
```

- **作品は「常緑ノートの一種」**(`kind: work`)。独立カタログにせず、ノートモデル
  に統一。作品は「作った経緯・学び」を育てられるので常緑側が自然
- 日付より **タグと相互リンク** で回遊させる

**log(ログ/ストリーム)** — `src/content/log/<YYYY-MM-DD>.md`

```yaml
title: その日の見出し
date: 2026-07-18         # ログは日付が主役
tags: [progress]         # 任意
```

- 日付順に流す。作業進捗・雑記・ふりかえり。書いたら基本いじらない
- 「毎日自動生成するか」は別問題(Todo 参照)。まず**手動で数本**置いて器を作る

> **なぜ2コレクションに分けるか:** 育てる常緑ノートと流すログは、更新リズムも
> 一覧の見せ方(タグ回遊 vs 時系列)も違う。1 つに混ぜると両方が中途半端になる。

### 2. 情報設計(このプロジェクトの主役機能)

参考元を超えるべき唯一の軸。**「探せる・繋がる」** を最優先で作り込む。

- **全文検索**: Pagefind(静的・バックエンド不要・日本語対応)。常に届く位置に置く
- **タグ**: `/tags`(全タグ)、`/tags/<tag>`(絞り込み)。回遊の主軸
- **目次(TOC)**: 常緑ノートは見出しから自動生成した目次を付ける(長文を育てる前提)
- **ノート間リンク**: 本文中の相互リンクを一級市民に。まず通常の Markdown リンク、
  次に **バックリンク(このノートを参照している他ノートの逆引き)** を持たせる
- **構造化されたトップ**: 逆時系列の羅列にしない。主要タグ / 育成中の常緑ノート /
  最新ログ、を面で見せて「構造が一目で分かる」入口にする

> **なぜ情報設計を核にするか:** 参考元の物足りなさが「探しにくい・構造が弱い」
> だったため。ここを凡庸にすると本プロジェクトを作る意味が薄れる。

### 3. 知見の追記フロー(Claude 運用)

- 会話で知見が溜まったら、Claude が常緑ノート or ログを書き出し、frontmatter を
  付けて commit / push。ホストが自動デプロイする
- 「md を 1 個置く → push → 反映」以上の手順を人間に要求しない
- 将来この手順を **garden-muse スキル**として型化する(Phase 3)。単なる登録に
  留まらず「好奇心ドリブンの着火(面白い方向・繋がりの提案)」まで担う。
  詳細は別紙 [`garden-muse-skill-spec.md`](garden-muse-skill-spec.md)

### 4. 見た目

- ミニマル・可読性最優先(KB は読む時間が長い)。ライト/ダーク両対応
- Astro ブログテンプレートが持つ SEO(canonical/OG)・サイトマップ・RSS を活かす
- 装飾より導線(検索・タグ・目次・リンク)を優先

## 非機能・開発方針

- **スタックは Astro**(参考元と同じ)。TypeScript・Content Collections・MD/MDX。
  npm / Node が前提(v1 の「ゼロ依存」方針は撤回。理由は下記)
- 設定値(サイト名・ベースURL・著者)は Astro 設定/環境変数に 1 箇所集約
- コンテンツとテンプレートを分離。ノート追加でテンプレートを触らない
- 公開前提。秘密情報を置かない

> **なぜ素 HTML から Astro に変えたか:** 旧仕様は「何年後でも動く」を理由に素の
> HTML/JS + 自前 Markdown を選んだ。だが憧れた完成度(タグ・検索・目次・リンク・
> RSS・OG・良い DX)を自前で積むと結局フレームワーク相当を再発明する。Astro に
> 乗る方が速く・堅く・拡張しやすい。ビルド環境が要る点は許容する。

## 開発の進め方(フェーズ分け)

1. **Phase 1 — ローカルで完結(ハード・ドメイン不要)**
   Astro プロジェクトを作り、`npm run dev` / `build`+`preview` で確認できる状態に:
   - Content Collections `garden` と `log`(zod スキーマで frontmatter 検証)
   - 常緑ノート一覧 / ノート詳細(**目次つき**)
   - ログ一覧(時系列)/ ログ詳細
   - タグページ(`/tags`, `/tags/<tag>`)
   - 作品ビュー(`/works` = `kind: work` の抽出)
   - **全文検索(Pagefind)**
   - **構造化トップ**(主要タグ + 育成中ノート + 最新ログ)
   - 本文中のノート間リンクが機能する(通常 Markdown リンク)
   - ライト/ダーク、最小スタイル
   - 種データ: 旧 `portal/works.json` の 3 件を `kind: work` の常緑ノートに変換 +
     常緑ノート数本 + ログ数本
2. **Phase 2 — 情報設計の仕上げ & 公開**
   - **バックリンク**(逆引き)と関連ノート表示
   - `[[wikilink]]` 記法(任意)
   - クラウド静的ホスト(Cloudflare Pages 推奨)に接続し git push 自動デプロイ。
     独自ドメインは任意で後付け
3. **Phase 3 — 追記運用の型化**: garden-muse スキル実装。会話→ノート/ログ案生成
   →承認→md 追記・commit を固定手順にし、あわせて好奇心ドリブンの着火提案を担う
4. **Phase 4 — デジタルガーデン強化**: 知識グラフ可視化、MOC(目次ノート)、
   RSS/OG の作り込み
