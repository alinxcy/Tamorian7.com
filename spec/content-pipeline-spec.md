# Content Pipeline — 知見を「拾う・書く・止める・繋ぐ」仕組み 仕様書 (v1)

> このドキュメントは `spec/knowledge-garden-spec.md` (v2) を**置き換えない。追加する**。
> v2 は「器」(Astro / 2コレクション / 情報設計) を定義した。本書は器の上で回る
> **運用パイプライン**——毎日の発見を流し、作業を実録に起こし、公開前に止め、
> ノート同士を地図で繋ぐ——を定義する。
>
> 判断の背景は各セクションの引用ブロックに残す。

---

## 概要

Knowledge Garden にはすでに「濃い実録が書ける」実績がある
(`src/content/log/2026-07-26.md` — Sakana Fugu の裏トークン実測)。
だがそれは**暗黙知としてたまたま上手くいった1本**であり、再現性がない。

本仕様の目的は、その1本を**型として固定し、毎回出せるようにする**こと。
具体的には **1つの Skill と 3つの Subagent**、それを支える最小限の実装を追加する。

- **Skill `tamorian7`(1つ)** — 会話中の捕獲。どの層に入れるかを判断し、
  一問だけ聞いて書く。判断基準は `references/` に分割して持つ
- **Agent `blog-curator`** — 興味に合う外部の記事・道具を探して束ねる
- **Agent `promotion-reviewer`** — 在庫を棚卸しし、昇格と破棄を提案する
- **Agent `honest-reviewer`** — 公開前に「言いすぎ」と「未確認」を指摘する

加えて、既存 Skill が抱える運用上の地雷 (反映先ブランチが SKILL.md 本文に
ハードコードされ、2リポジトリで二重管理になっている) を
**設定ファイルの外出し**で解消する。

> **なぜ「記事生成」ではなく「パイプライン」なのか:** 単発の記事生成なら Skill は
> 要らない。会話でその都度頼めばよい。Skill にする価値があるのは、**層をまたぐ判断**
> (この種は昇格に値するか / この記述は言いすぎか) を毎回同じ基準で下せるようにする点
> にある。よって本仕様の中心は文章生成ではなく**判定基準**である。

## コンテンツモデル (4層) と命名

> **なぜここで作り直すか:** v2 は作品を「常緑ノートの一種 (`kind: work`)」として
> 定義した。だが運用してみると **Garden ノートと Works の違いが説明できない**という
> 症状が出た。原因は理解不足ではなくモデルの誤りである——
> **Garden は「主題」で切る横串、Works は「プロジェクト」で切る縦串**であり、
> そもそも階層が違う。同列に置いたから混ざった。本節でこれを分離する。

### 4層の役割

| | seeds | log | garden | works |
|---|---|---|---|---|
| **主語** | 他人の成果 | 自分がやったこと | わかったこと | 作っているもの |
| **切り口** | — | 日付 | **主題** | **プロジェクト** |
| **時間** | 拾った日 | 作業した日 | 日付は脇役 | 状態が主役 |
| **書き換え** | status のみ | しない | する | する |
| **トリガー** | 毎日 | 作業の区切り | 2回目に気づいたとき | 作り始めたとき |
| **寿命** | 使い捨て | 化石 | 育つ | 完成したら取説になる |

seeds と log が**原料**、garden と works が**製品**である。
原料は増える一方でよい。製品は数を絞って育てる。

### 命名とナビゲーション

表示名を英語に統一する。URL は既に英語なので一致させる。

| 表示名 | URL | 中身 |
|---|---|---|
| Garden | `/garden/` | 主題単位のノート |
| Log | `/log/` | 実録 |
| Works | `/works/` | プロジェクト |
| Tags | `/tags/` | 横断 |
| Search | `/search/` | 全文検索 |

- 「常緑ノート」は廃止し **Garden** とする (日本語として不自然だったため)
- seeds はナビに出さない (詳細ページ `/seeds/<slug>/` は持つ)
- **サイト名を「Knowledge Garden」から確定させること。**
  セクション名が Garden になるため、サイト名と衝突して指示語が曖昧になる。
  ヘッダのロゴはサイト名 (例: `Tamorian7`)、その下のナビが Garden / Log / Works、
  という関係が明確になる名前を選ぶ。v2「次のアクション 3」の宿題をここで回収する

### works コレクション

`src/content/works/<slug>.md` として **garden から独立させる**。

```yaml
---
title: fugu-lab
status: wip                # planned | wip | published
emoji: 🐡
repo: https://github.com/alinxcy/fugu-lab
url:                       # 公開URLがあれば
summary: Fugu の課金トークンを実測するチャットアプリ
updated: 2026-07-26
publish: true

# 作業中だけ持つ。published にするとき削除する (後述)
chats:
  - label: 仕様の壁打ち
    kind: claude              # claude | code
    url: https://claude.ai/chat/xxxxxxxx
  - label: 実装セッション
    kind: code
    session: 0a1b2c3d
---
```

garden / log / seeds 側には**任意の `project` フィールド**を足す。

```yaml
project: fugu-lab          # works の slug。無いノートがあってよい
```

これにより Works の詳細ページが**手作業ゼロで集約ハブになる**:

```
Works / fugu-lab  🐡  [制作中]  repo ↗

  ■ 作業場 (status: wip のとき) / 使い方 (status: published のとき)
  ■ このプロジェクトから生まれたノート   ← project: fugu-lab を自動収集
  ■ 作業ログ                            ← 同上
```

> **なぜ `kind: work` のままにしないか:** 集約だけなら `project` を足せば足りる。
> だが Garden 一覧に作品が混ざり続ける限り「両者の違いがわからない」という
> 元の症状は消えない。**一覧が分かれて初めて、役割の違いが目で理解できる。**
> 移行対象は現状4〜5ファイルであり、独自ドメイン移行前のいまが最も安い。

### Works の三態 — 作業場から取説へ

`status` によって**本文に書くことが入れ替わる**。ここを型にしないと、
Works ページは「作りかけの散らかった机」のまま放置される。

**`planned` (構想中)** — なぜ作りたいか、解きたい問題。仕様書へのリンク。短くてよい。

**`wip` (制作中) = 作業場** — 書くのは3つだけ:

1. いま**動いているところ**
2. いま**詰まっているところ**
3. **次の一手**

**この3つは毎回上書きする。履歴を残さない。**
作業場は机であり、散らかったら片付けるものだから。

**`published` (公開)** — 主役が**使い方**に入れ替わる。
何ができて、**何ができないか**。既知の限界。作業場の記述はここで消える。

### chats — 作業中だけ生きるリンク

作業に対応する AI との会話へのリンクを `chats[]` として持つ。
**ただし `planned` / `wip` のときだけ表示し、`published` にする際に削除する。**

| kind | 出し方 | 他人が開けるか |
|---|---|---|
| `claude` | URL リンク | 開けない (本人の認証が要る) |
| `code` | `claude --resume <session>` をコピーボタンで | ローカル再開のみ・同一マシン前提 |

- ページ**下部に「作業リンク (自分用)」として折りたたむ**。
  経緯を辿る第一候補は log と spec であり、chats は最後の砦という位置づけ
- **公開共有リンク (share) は使わない。** 会話の全文が出るため、
  試行錯誤の途中の誤り・捨てた案・貼った値がそのまま公開される。
  見せたい経緯は log に書く

> **なぜ作業中に限定するか:** チャット URL は腐る。会話を消せば 404 になり、
> しかも壊れても気づかない。**リンクの寿命と、それが表示される期間を一致させる**
> ことで、この問題を構造的に消す。作業中なら会話はまだ生きている。
>
> 副産物として、**残っている `chats` は「まだ log に吐き出していない会話」の
> マーカー**になる。`published` へ移す作業が、リンクが腐る前の最後の締切として働く。

**機械判定を1つ追加する** (honest-gate 参照):
`status: published` なのに `chats` が残っていたら warn。
「log に吐き出したか / 消したか」を必ず通過させる。

### 作業場 → log への吐き出し

作業中に溜まる「面白かったこと」「転んだこと」は机の上に置いておけない。
**溜まったら log に実録として切り出す。**

```
works (作業場)  ──溜まったら──▶  log (実録として日付で固定)
                                    │
                                    └─ 一般論があれば ──▶ garden
```

**log は溜め場ではなく吐き出し先である。**
この経路があるおかげで、完成時に作業場を消して使い方に書き換えても、
**転んだ記録は log に残り、経緯が失われない**。
Works ページは読みやすく保たれ、かつ歴史は消えない。

## 実行の分担 — 捕獲は Skill、加工は Agent

> **なぜ分けるか:** Skill は**いまの会話の中**で動くのであなたと往復できるが、
> やり取りが会話に全部残る。Subagent は**別コンテキスト**で動くので会話は汚れないが、
> **走っている間あなたは割り込めない**。「相談したい」と「汚したくない」は、
> そのままでは両立しない。

**時点で切ることで両立させる。**

| | 担当 | 理由 |
|---|---|---|
| 拾う瞬間(会話中) | **Skill** | 判断は Yes/No 一問で足りる。往復が要る |
| 在庫の棚卸し・昇格判定 | **Agent** | 全ファイルを読む。会話中にやる必要がない |
| 外部を探して束ねる | **Agent** | 探索ログが長い。結論だけ欲しい |
| 公開前レビュー | **Agent** | 指摘が多く会話を埋める |

判断が要る作業は、そもそも会話の最中ではない。だから分けられる。

### Skill を1つに統合する

Skill は description のマッチで起動するため、**数が増えるほどどれが出るか
読めなくなる**。1つにまとめれば起動条件が「Tamorian7 を触るとき」で済み、
予測可能になる。

肥大を防ぐため、SKILL.md は**薄い交通整理だけ**にし、詳細は必要になった時点で
参照する。

```
.claude/skills/tamorian7/
  SKILL.md                       ← どの層に入れるかの判断だけ。薄く
  references/seeds.md            ← 種の型と why の書き方
  references/devlog.md           ← 実録の型(4セクション)
  references/works.md            ← 三態と chats
  references/honest-gate.md      ← 止める基準
  references/retro-capture-prompt.md
.claude/agents/
  blog-curator.md
  promotion-reviewer.md
  honest-reviewer.md
```

**既存の `garden-muse` はこの Skill に吸収する**(ペルソナ・公開確認・食い下がりを
そのまま引き継ぐ)。2リポジトリ二重管理の地雷は `garden.config.json` の外出しで解消。

### 会話中は「一問だけ」

会話が汚れる原因は Skill であること自体ではなく、**拾う瞬間に長く相談すること**。

- 拾う瞬間は Yes/No で答えられる**一問だけ**
- タグ・要約・本文の相談を会話中に始めない。承認後に下書きを出す
- 断られたら即引く。同じ会話で二度聞かない

## コンポーネント仕様

### 0. `garden.config.json` — 設定の単一情報源

**これを最初に作ること。** 以降の全 Skill はハードコードを持たず、
リポジトリルートの `garden.config.json` を読んでから動く。

```jsonc
{
  "repo": "alinxcy/Tamorian7.com",
  "branch": "main",              // 反映先。ここだけ直せば全 Skill が追従する
  "paths": {
    "garden": "src/content/garden",
    "log":    "src/content/log",
    "works":  "src/content/works",
    "seeds":  "src/content/seeds",
    "widgets":"public/widgets"
  },
  "promotion": {
    "seedThreshold": 3,          // 同タグの kept がこの数を超えたら昇格提案
    "staleDays": 30,             // inbox のまま腐ったら dropped 提案
    "mocMinTagCount": 5          // タグ数がこれ未満なら地図は作らない
  },
  "feeds": [
    { "id": "hn",    "url": "https://hnrss.org/frontpage", "weight": 1 }
    // 実装時に追加。空配列でも動くこと
  ],
  "honestGate": {
    "bannedPhrases": ["絶対", "必ず", "間違いなく", "完全に", "誰でも簡単に"],
    "allowWithReason": true      // 直後に理由コメントがあれば通す
  }
}
```

> **なぜ外出しするか:** 現状 garden-muse の反映先ブランチは SKILL.md 本文の設定表に
> 書かれており、`Tamorian7.com` と `claudePlayGround` の2箇所を手で直さないと
> 片方が古いブランチに書き続ける (v2 仕様の「次のアクション」に警告として明記されている)。
> Skill を4つ増やせばこの地雷も4倍になる。**設定は本文ではなくリポジトリに置き、
> SKILL.md には「garden.config.json を読め」とだけ書く。**
> 既存の garden-muse も同じ形に移行すること。

### 1. seeds コレクション

`src/content.config.ts` に3つ目のコレクションを追加する。

```yaml
---
title: カメラの上でLLMが動く reCamera Pro
found: 2026-07-27          # 拾った日
url: https://...           # 出典 (必須)
source: hn                 # garden.config.json の feeds[].id、手拾いは "manual"
tags: [edge-ai, vlm]
why: 3 TOPS でVLMがオンデバイス。ローカル構成の判断が変わるかもしれない
status: inbox              # inbox | kept | promoted | dropped
promotedTo: /garden/xxx/   # promoted のときだけ
publish: false             # 既定 false。kept にしたものだけ true にしうる
---

任意の本文 (無くてよい)
```

**必須は `title` / `found` / `url` / `why` / `status`。**

#### `why` を必須にする理由

URL とタイトルだけの拾いものは3ヶ月後の自分にとって無価値になる。
「なぜ気になったか」の1〜2行だけが、後で昇格を判断する材料になる。
逆に言えば **why が書けない拾いものはその場で捨ててよい**。
これが seeds 層の存在意義そのものである。

#### 専用一覧ページを作らない理由

seeds はストックではなくフローである。`/seeds/` という一覧を作ると
それが実質ブログになり、「garden が主役」という v2 の設計がぶれる。
代わりに**2箇所にだけ**露出させる:

- **トップページに「未昇格の在庫: N件」** — 読ませるためではなく
  「片付けろ」という圧として機能させる。件数と、直近3件程度で十分
- **`/tags/<tag>` に garden / log / seeds を混ぜて出す** — これが本命。
  「edge-ai について自分は何を持っているか」が、常緑ノート1本・ログ2本・種5件、
  と一望できる。v2 が核に据えた情報設計と直接噛み合う

> **なぜ log に混ぜないか:** v2 は「育てる常緑ノートと流すログを混ぜると
> 両方が中途半端になる」と決めた。同じことが log の内部でも起きる。
> `log/2026-07-26.md` のような濃い実録と「今日見つけた面白い論文」が同じ一覧に並ぶと、
> 濃い方が薄い方に埋もれる。v2 の Todo に残っている「ログの毎日自動生成(未決)」は、
> おそらくこの分離ができていないために決められなかった。本仕様でそれを解く。

### 2. 種を拾う — chat mode(主)と feed mode(従)

**会話から拾うのが主、フィードは補助。**

> **なぜ会話が主か:** フィードから拾う場合「自分の文脈に繋がるか」を推定する必要が
> ある。だが会話に出てきたものは**繋がりが自明**——その話題が出た理由が会話に
> そのまま残っている。つまり seeds で一番書くのが面倒な `why` が、
> 会話由来ならタダで手に入る。
>
> 当初この仕様はフィード収集だけを書いていた。これは書き手の見落としだった。

#### chat mode(Skill `tamorian7` が担当)

**拾う条件は「脱線したもの」。本筋なら今やる。逸れたから種になる。**

- ユーザーが貼った URL
- 話の流れで出てきた道具・論文・製品で、いまは追わないもの
- 「へえ」と思ったが本筋ではなかったもの

自発的に一問だけ聞いてよい(読み取りのみで安全)。ただし**脱線を全部拾わない**——
拾いすぎると inbox が即座に腐る。AI が勝手に登録せず、**提案して承認**を取る。

#### feed mode(Agent `blog-curator` が担当)

`garden.config.json` の `feeds[]` を読む。**空配列でも機能する**
(むしろ Phase 2 は空で始めるのが正しい)。

一次選別は既存タグ集合との近さで行う。**「面白いか」では選ばない**——
面白い記事は無限にあり基準として機能しない。「すでに持っている文脈に繋がるか」で
選ぶと、拾った時点で昇格の芽があるものだけが残る。

興味プロファイルは外部に作らない。**garden のタグと本文、seeds の `why` が
そのまま興味の記述**である。

#### 在庫の見張り(Agent `promotion-reviewer` が担当)

- `inbox` のまま `staleDays` 超え → `dropped` を提案
- 同じタグの `kept` が `seedThreshold` 超え → garden ノートの種として提案
- log を横断して**同じ転び方が2回以上** → 判断基準ノートとして提案(最も価値が高い)

### 3. 実録を書く — log の型(references/devlog.md)

**役割** — 作業の記録から実録記事 (`log/`) の下書きを起こす。

**トリガー** — 作業が一区切りついたとき。「今日のログ書いて」等の依頼。
`skill-harvester` と役割が近いが、**あちらは手順の抽出、こちらは記事化**で分担する。

#### 記事の型 (`log/2026-07-26.md` から逆算した構造)

1. **なぜやったか** — 1〜2文。「判断のため」「予習のため」など動機を明示
2. **実測でわかったこと** — 箇条書き。**数字には必ず単位と測定条件**を付ける
3. **実装で刺さった罠** — 番号付き。**自分のバグを必ず含める**。
   「ライブラリが悪かった」だけで終わっている記事は薄い
4. **未確定のまま残したこと** — n数と、**なぜ結論にしなかったか**
5. **一般論の切り出し** — 判断基準に昇格する部分は garden ノートへ分離してリンク

> **なぜこの型か:** 既存の 07-26 の記事がこの構造を持っており、実際に読み応えがある。
> 特に効いているのは 3 と 4 である。3 の「自分のバグ」は当事者にしか書けない情報で、
> 他所からコピーできない価値になる。4 は書き手の誠実さを担保すると同時に、
> 後日の再検証タスクとして機能する。

#### 入力: 記録の仕込み (Phase 1 で導入)

**実録の厚みは書く技術ではなく、転んだ瞬間の時系列が残っているかで決まる。**
事後に「今日のこと書いて」と頼んでも、成功した最終形しか復元できない。よって:

- **wip コミットを潰さない。** 失敗中の状態も
  `wip: SPIの応答が全部0x00` のように**症状をコミットメッセージに書いて**残す。
  squash して歴史を綺麗にしない。ここが記事の骨になる
- **`scratch/YYYY-MM-DD.md` に作業中の転びを追記する。** 整形不要・箇条書き・
  時刻付き。`.gitignore` に入れず、リポジトリに残す (公開したくなければ
  `publish` 対象外のディレクトリに置く)
- 計測値・スクリーンショットは timestamp 付きで一箇所に落とす

devlog-writer は `git log`(当該期間の wip 込み) と `scratch/` を読んで下書きを作る。

**足りない場合は書かずに問う。** 型の 3 と 4 が埋まらないときは、
勝手に埋めずに「本当に何も転ばなかったか」「その数字は何回測ったか」を聞き返す。

### 4. 公開前に止める — honest-gate(references/honest-gate.md)

**役割** — 公開前に「言いすぎ」と「未確認」を止める。

> **なぜ必要か:** 既存の `log/2026-07-26.md` 自身が必要性を実証している。
> 同記事には「比率の分母を表だけにしていたバグは、極端なデータが来て初めて露見した」
> 「興奮して確定事実として書きかけたところを止めてもらえた」と書かれている。
> 止める役は**実在の需要**であり、かつ**そのときは人間がたまたま止めた**だけである。
> また garden の既存ノートに「読者に指摘されて直した」系の記録がある以上、
> 事前に自分でやる価値がある。

**2段構成にする。** 混ぜると、機械で確実に落とせるものまで AI の気分に左右される。

#### (a) 機械判定 — CI でブロック

`npm run check` として実装し、GitHub Actions から呼ぶ。落ちたらマージさせない。

- frontmatter スキーマ違反 (既存の zod で既に担保。CI に組み込むだけ)
- **内部リンク切れ** — `/garden/<slug>/` の実在確認
- **base パス忘れ** — GitHub Pages 配信時の `/Tamorian7.com/` 欠落。
  既存ノート `github-pages-astro-gotchas.md` に記録済みの実際の転び
- 生の数式記法 (`$...$`) が未レンダリングで残っていないか
- **`status: published` の works に `chats` が残っている** → warn。
  腐るリンクが公開状態で残るのを止める (「Works の三態」参照)
- **禁止語** (`honestGate.bannedPhrases`) — 既定は warn。
  ただし `allowWithReason` が有効なら、直後に理由コメントがある場合は通す

#### (b) AI 判定 — 書くときに問う (CI には入れない)

- **n=1 の観測を一般法則として書いていないか。** 「〜する傾向がある」と
  書かれた根拠のサンプル数を確認する
- **確認していない既定値を、確認済みのように書いていないか**
- **数字に単位と測定条件があるか**
- **失敗・限界の記述があるか。** 無いなら「本当に何も転ばなかったか」と問う
- **断定の強さが根拠に見合っているか**

> **なぜ AI 判定を CI に入れないか:** CI で LLM を呼ぶと API キー・課金・
> 実行時間の管理が要るうえ、判定がぶれるとマージがランダムに詰まる。
> **機械は止める、AI は問う**、と役割を分けた方が運用が壊れにくい。
> (将来 PR コメントとして非ブロッキングで足すのは Todo。)

### 5. 地図を作る — MOC(Agent promotion-reviewer が提案)

**役割** — タグとノート間リンクを走査し、MOC (Map of Content = 読む順の地図) を再生成する。

**起動条件** — `promotion.mocMinTagCount` 以上のタグが存在するとき、または手動。

> **なぜ起動条件を付けるか:** 現在ノートは8本程度である。この規模で地図を作っても
> 地図の方がノートより長くなり、意味がない。**地図は迷子が発生してから作る。**
> ただし仕組みは先に用意しておき、閾値を越えた時点で自動的に提案が出るようにする。

**出力** — `src/content/garden/moc-<topic>.md` (`kind: note`, tag に `moc`)。

- 該当タグのノートを**読む順**に並べる (前提 → 応用の順。日付順にしない)
- 各ノートに1行の「なぜここで読むか」を添える
- **穴を明示する** — 「この間を繋ぐノートがまだ無い」を書く。
  これが次に書くものの候補リストになる

**やらないこと** — 知識グラフのビジュアル化 (v2 の Phase 4 のまま据え置き)。

### 6. widgets — 触れるデモの受け皿

**方式**: `public/widgets/<slug>/index.html` に**単一ファイル HTML** を置き、
記事から `<iframe>` で埋め込む。高さは frontmatter か埋め込み時に指定。

```
public/widgets/euler-step/index.html   ← CSS/JS 込みで1ファイル
```

記事側 (MDX):

```mdx
<Widget slug="euler-step" height={480} title="オイラー法を1コマずつ" />
```

> **なぜ Astro islands (React 等) にしないか:**
> (1) 単一ファイル HTML はフレームワークの寿命に依存せず、何年後でも開ける
> (2) 別サイトへそのまま持ち出せる。ローカルに落として動かすこともできる
> (3) 外部依存が無ければローカル LLM でも生成・改修できる
> (4) 参考元 (tnks1407) が72個の実験を運用できているのは、おそらくこの粒度だから。
> ビルドに巻き込まれない代わりに、共通スタイルは各ファイルにコピーされる。
> **その重複は許容する** (寿命と引き換え)。

**制約 (v1 で許容する限界)**: CDN 依存を禁止しない。ただし使う場合は
バージョン固定 (`@1.2.3`) とし、切れたときに図が消えることを記事側で前提にしない。

## 非機能・開発方針

- **v2 の方針をすべて継承する。** Astro / Content Collections + zod /
  Pagefind / 静的ホスト / 入口は git push のみ

- **Skill は `tamorian7` の1つだけ。** 既存 `garden-muse` は吸収し、

- **重い作業は Subagent に出す。** 会話を汚さないため、および Skill を薄く保つため
- テスト: 機械判定 (`npm run check`) はユニットテストを持つこと。
  意図的に壊した fixture を用意し、確実に落ちることを確認する
