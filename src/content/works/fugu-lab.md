Fugu に毎月お金を払う価値があるかを判断するための計測環境。性能の評価でも
比較記事でもなく、**自分が実際に使った記録**を集めて、月額に見合うかを決める。

だから**律速はコードではなくデータ**になる。アプリをいくら磨いても、
使わなければ判断材料は1件も増えない。判断期限は2026年9月末。

## 三つの部品と、唯一の結合点

複雑に見えるが、構造は単純だった。**書く側**と**読む側**があり、
その間に**一枚の契約**が挟まっている。

| ディレクトリ | 役割 |
|---|---|
| `chat/` | Fugu を叩くチャットアプリ。応答を受けながら使用量を記録する |
| `schema/usage-record.md` | **唯一の結合点。**両側の共通言語 |
| `dashboard/` | JSONL を集計して「契約すべきか」を出す |

記録は `data/usage.jsonl` に1行1レコードで追記される。ダッシュボードは
末尾差分だけを読む。**スキーマを変えると両側が動く** —— それが意図された
設計で、だから定義は1箇所にしかない。

四つ目の入口として `tools/fugu_offload.py` がある。機械的な下請けを Fugu に
投げる CLI で、**既定でチャットアプリを経由する**。つまり**外注1回が測定1件になる**。
判断材料を作るために無理やり使う、という不自然さを消すための設計。

## 表と裏 — 何を測っているのか

Fugu は**自分自身にサブタスクを委任する**モデルで、委任・検証・統合・再帰呼び出しに
使われたトークンが `orchestration_*`。ここでは**「裏」**と呼んでいる。

効いてくるのは、**裏も通常と同じレートで課金される**こと。画面には出ないのに
請求書には出る。**裏率はそのまま支払いの水増し率**になる。

| モデル | 裏 | レイテンシ | 位置づけ |
|---|---|---|---|
| `fugu` | 観測範囲で常に 0 | 数秒〜30秒 | 単一モデル的。速い |
| `fugu-ultra` | 78〜98% | 287秒 / 427秒 | fan-out する。重い |
| `fugu-cyber` | 未確認 | — | — |

### トークン比率と金額比率はズレる

ある ultra のレコードで、裏率は**トークン基準で78%、金額基準では約63%**だった。
output のレートが input の6倍あるので、可視 output が大きいと比率が動く。

**判断はお金でするので、金額基準の裏率を出す必要がある。**
トークン比率だけ見ていると読み違える。

### 裏が0でも安いとは限らない

base `fugu` は裏0だが、単純なコード生成でも `completion_tokens` の大半が
`reasoning_tokens` だった(744 のうち 650、表示された回答は約94トークン分)。
**裏が0でも「見えない思考コスト」は別枠で存在する。**

## 壊してはいけないもの

スキーマの「譲れない要件」。共通しているのは
**「記録されなかったデータは復元できない」**という一点で、あとで直せる類ではない。

- **SSE 層でチャンクの `content` 以外を捨てない。**ストリーミングでは `usage` が
  最終チャンクに載る。捨てると記録が成立せず、プロジェクト全体が無意味になる
- **`raw_usage` を無加工で保存。**唯一の保険。マッピングを誤っても後から直せる
- **`ttft_s` と `elapsed_s` を分ける。**「反応が始まるまで」と「終わるまで」は
  体感が別物で、合算すると分離できない
- **null と 0 を区別する。**「裏が0だった」と「裏が取れなかった」は別の意味
- **レコードは1件生成する。**失敗しても、欠けても作る。
  「取れなかった」という事実も記録として価値がある

## 外注のルール

実測から出た運用指針。核は一行に畳める ——
**「生成が重く、検証が軽い」ものだけ投げる。**

```
外注で節約 = 自分で生成するコスト
外注で発生 = 委任prompt作成 + 出力の検証・手直し + API実費
→ 生成が大きく機械的で、検証が自動化できるときだけ純利益
```

つまり**「出力を結局ぜんぶ精読しないと使えない」ものは外注しない。**
それなら自分で書くのと変わらない。

| 投げる(base fugu) | 手元に残す |
|---|---|
| 定型コード生成 — 実行して検証 | アーキテクチャ・設計判断 |
| 自由文 → JSON 抽出 — スキーマ検証 | セキュリティ上重要なコード |
| 正規表現・SQL — サンプルに当てて実行 | 仕様そのものの執筆 |
| 翻訳・要約の下書き — 原文照合 | 静かに誤ると致命的な集計ロジック |

判断の基準そのものは [AIに任せる仕事の切り分け](/garden/ai-offload-criteria/) に。

**ultra は外注に使わない。**裏80〜97%、数秒〜7分、そして
**本文が空のまま課金される**ことがある。reasoning が `max_tokens` を食い尽くして
可視出力ゼロ、しかし裏は12,364トークン、という実測がある。下請けは base 一択。

## 詰まりは解けた — 記録は249件になった

**「記録が1件しかない」と書いていた頃の原因は、チャットアプリを起動していなかった**
だけだった。既定はアプリ経由で、落ちていると直接 API に回り、その経路は記録されない。

`systemd --user` の常駐にして、**手起動をやめた**。
その後 **2026-08-26 に1日で221件**投げ、**枠を使い切った。**

## 枠の形が測れた（2026-08-27）

**日次ではなかった。「最初の1回」で5時間の窓が開く。**

```
枠の開始      終了     件      トークン
08-26 10:55  15:55    95    482,759
08-26 17:34  22:34    22    200,201
08-26 22:55  03:55   104    600,332   ← ここで枠切れ
```

API が返した「03:55 以降に再試行」は **22:55 のちょうど5時間後**。
上限は挟めただけで、**48万は通り 58万で落ちる。**

→ [枠は日次ではない](/garden/five-hour-window/)

## 応答の特性（240件から）

```
入力の大きさ    n    入力中央   出力中央   推論%   最初の1文字まで   所要
〜1k           23      188      155    61%       3.9s      4.2s
1〜4k          90    2,747    1,266    30%       8.1s     17.9s
4〜10k        125    5,477    1,022    31%       7.7s     18.2s
```

**入力が20倍でも、最初の1文字までの時間はほとんど変わらない。**
所要は出力の長さで決まり、**毎秒66〜69トークンで一定**だった。

- **渡す量をケチっても速くならない。** 分けて何度も投げる方が遅い
- **短く返させることだけが効く**
- **小さい依頼ほど割に合わない。** 入力1k未満は**出力の61%が推論**
- **キャッシュ済み入力は 4.7%。** 手元の主力（キャッシュ読が出力の289倍安い）の
  設計をそのまま持ち込むと外す

→ [外注の損益分岐](/garden/ai-offload-criteria/)

## フォールバックは一度も動いていなかった

枠切れのとき直接 API に落ちる作りだったが、**成功したことが一度も無かった。**
鍵は `fugu-chat.service` が環境変数で渡していて、**CLI から呼ぶと届いていなかった。**

**普段は一段目が通るので、壊れていることを知る機会が無い。**
一段目を死んだポートに向けて二段目だけを通し、直したのを確認した。

**ただし枠切れの受け皿にはならない。** 枠はアカウント単位なので、
経路を変えても同じ壁に当たる。**効くのはアプリが落ちているときだけ。**

**二重化は「何に対する二重化か」を言えないと意味を持たない。**

## 次の一手

1. **ローカル LLM で同じ索引が作れるか試す。** 届けば契約の根拠が消える
2. **`ttft_s` を `number | null` にして、直接経路でも記録する。**
   スキーマ・`chat/`・`dashboard/core/record.py` をセットで直す。
   結合点なので片方だけ触らない
3. **大きいバッチは窓の頭に置く。** 窓の途中で始めると全滅する。
   小さい1回が窓を開けてしまうことにも注意

**「使う用事がない」という詰まりは解けた。** 他のAIとの長い会話ログに索引を
作らせる用事が見つかり、**1日で221件・128万トークン**まで伸びた。
定型的で、検証が軽く、毎回発生する —— 外注の条件をちょうど満たしていた。

過去の9件は**復元しない。**端末のスクロールバックから拾って書き戻すのは、
記録としては捏造に近い。判断期限は2026年9月末。
