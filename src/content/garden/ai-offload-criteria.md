エージェントが別のモデルに仕事を振れるようになった。ここで素朴に考えると
「重い処理を安いモデルに投げれば得」だが、実際に何度か外注してみると、
そう単純ではないと分かる。

## 損益分岐は「検証コスト」にある

```
外注で節約できるもの = 自分で生成するコスト
外注で新しく発生するもの = 委任プロンプトを書く手間
                          + 出てきた出力を検証・手直しする手間
                          + API 実費
```

つまり **生成が重く、かつ検証が軽いときだけ純利益が出る。**

ここで効くのは生成コストではなく検証コストのほうだ。
**「出力を結局ぜんぶ精読しないと使えない」タスクは外注してはいけない。**
それなら自分で書くのと手間が変わらないどころか、他人の書いたものを読む分だけ遅くなる。

## 「検証が軽い」の具体

検証が次のどれかで**機械化できる**なら、安心して投げられる。

- **実行できる** — 生成コードをテストに通す
- **スキーマ検証できる** — JSON を定義に照らす
- **完全一致で照合できる** — 日付計算、単位変換

逆に「読んで妥当性を判断するしかない」ものは、検証が生成と同じ重さになる。

## 振り分け表

**外注してよい** — 定型コード生成(パーサ・変換・雛形)、自由文から構造化データへの抽出、
正規表現や SQL、翻訳、一次要約のドラフト、テストの雛形やダミーデータ。

**手元に残す** — アーキテクチャや設計判断、セキュリティ上重要なコード、
会話の文脈やユーザーの意図に依存する最終回答、仕様そのものの執筆、
そして**壊れても静かに間違った答えを出し続ける類の処理**(集計ロジックなど)。

最後のものが一番危ない。壊れたら落ちてくれるコードは外注できるが、
静かに誤るコードは検証が事実上不可能なので手元に置く。

## 実際にやってみて踏んだ罠

実測では、コード生成・JSON 抽出・正規表現・翻訳・要約の5種を投げて全部通った
(いずれも数秒〜10秒台)。ただし運用で3つ躓いた。

1. **出力形式を縛らないと前置きが付く。** 「コードのみ」「JSONのみ」と明示しないと、
   自己紹介や解説が混ざってそのままパイプできない
2. **思考過程(CoT)が最終出力に漏れることがある。** 英語の内部メモが本文に紛れ込む。
   機械処理する前にコードブロックや JSON 部だけ切り出すサニタイズを噛ませる
3. **出力トークンの上限をケチると空返しになる。** 推論(reasoning)がトークン枠を
   食うモデルでは、枠が小さいと**課金だけ発生して本文が空**で返る

3 が地味に痛い。外注は「安く済ませる」動機で始めるので、上限を絞りたくなるのだが、
絞りすぎると払い損になる。

## 一般化

この判断式は特定のモデルやサービスに依存しない。ローカル LLM に振るときも、
安価な API に振るときも、人に頼むときすら同じ形をしている——
**「自分でやるより、頼んで検算するほうが安いか」** だけを見ればいい。

そして面白いのは、この「検証が自動化できるか」という問いが、
**ベンチマークを設計できるかという問いと同じ形**をしていることだ。
自動採点できる問いは外注もできる。逆もまた然り。

## 追記(2026-08-26): 分岐は検証コストではなく、文脈に残る量だった

上の「検証コスト」は間違いではないが、**支配項を外していた。**
測り直したら、比べるべきものが違った。

```
全セッション合計   ターン 4,431 / 出力 4,749,675 / キャッシュ読 1,372,763,355
キャッシュ読 / 出力 = **289 倍**
```

**「1回読むだけ」というものは存在しない。** 読んだものは文脈に残り、
以降のリクエストごとに再課金される。**長いセッションでの残りターン数の中央値は 97。**

→ **判定は「Claude の文脈に最終的に何トークン残るか」だけで決まる。**

| 形 | 文脈に入るもの |
|---|---|
| 自分で読んで要約する | **元データ全部 + 答え** |
| スクリプトが外注先に流す | **答えだけ。元データぶんが丸ごと消える** |
| サブエージェントに読ませる | **答えだけ**（元は向こうで死ぬ） |
| 自分でプロンプトを書いて渡す | **プロンプト + 答え。純増する** |

**4番目が損なのは、入力を自分の文脈から書いた時点で元データが既に入っているから。**

### ただし「倍率」も言いすぎだった

compact の区切りを測ったら、**大きいものを読むと compact が早く来る。**
区切りのターン数は中央値 374 / 最大 1,255。
**「倍率がかかる」より「天井のある予算を食う」**の方が近い。n=4 で手動 compact が混ざるため、
**どちらが実態かは決着していない。**

### 「頼む」を「渡す」に変える

外注先に**「固有名詞をそのまま残せ」と頼んだら、残存率 6.2%** だった。
**正規表現で全部抜いて原文と一緒に渡したら 62〜87%** になった。

**機械にできることを機械に移すと、モデルの気分に依存しなくなる。**
そして移した部分は、**モデルを変えても契約をやめても、そのまま動く。**

### 指標は範囲で持つ

6.2% を直そうとして上限を外したら、**索引が原文より大きくなった。**
**測れる指標を作ると、それを最大化しに行く。**
上限だけ・下限だけの指標は壊れる。**さらに小さい入力では割合の上限が効かない**ので、
絶対値の下限も要る。

### 一番こわいのは、失敗しないバグ

**残存率 6.2% の索引が、数週間だれにも気づかれずに残っていた。**
出力は「ちゃんとしたもの」に見えていて、エラーも出ない。**測って初めて分かった。**

→ **外注には必ず、機械で測れる品質指標を1つ以上付ける。**
