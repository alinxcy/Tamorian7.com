一晩で大量に投げていたら、委託先が枠切れで止まった。

```
Subscription window is exhausted. Try again after 2026-08-26T18:55:30Z
```

**「1日いくら」だと思って組んでいた。** 違った。

## 実測

利用ログを、**5時間の窓が「最初の1回」で開く**という仮説で切り直す。

```
枠の開始      終了     件      トークン
08-26 10:55  15:55    95    482,759
08-26 17:34  22:34    22    200,201
08-26 22:55  03:55   104    600,332   ← ここで枠切れ
```

**API が返した「03:55 以降に再試行」は、22:55 ちょうど5時間後。**
偶然で一致する数字ではない。**窓は日付ではなく、自分の最初の1回で開いている。**

上限そのものは挟めただけで、まだ点で押さえられていない。

```
482,759 トークン   通った
584,493 トークン   ここで落ちた
```

**48万は通り、58万で落ちる。** 間のどこかにある。

## 何が変わるか

昼に **39.7万トークンを1時間で使っても落ちなかった**。
夜は **60万を45分で使って落ちた**。総量ではなく、**どの窓に入ったか**で決まっている。

- **大きいバッチは窓の頭に置く。** 窓の残りが分からないまま突っ込むと途中で全滅する
- **小さい1回が窓を開ける。** 22:55 に投げた 3,443 トークンの用事が窓を開け、
  その5分後に始めた本番のバッチは、**開いたばかりの窓ではなく「もう始まっている窓」に入った**
- **日をまたいでも回復しない。** 待つ先は 0時ではなく、**窓が開いた時刻＋5時間**

## 2度目だから書いている

**手元の主力も同じ形をしている。** 5時間の窓が最初の1回で開き、
窓の中で上限に当たり、窓が明けると戻る。別々の会社の別々のサービスで同じ構造が出た。

**「日次で割る」という直感が、そもそも合っていない。**
使う側から見ると、これは**残高ではなく予約席**に近い。席を立った時刻から数える。

## ついでに見つかった、効いていないフォールバック

枠切れのとき、アプリ経由から直 API に落ちる作りにしてあった。**動いていなかった。**

```
[warn] chat アプリ経由に失敗(...)。直接 API にフォールバックします
RuntimeError: FUGU_API_KEY が見つかりません
```

**二重化したつもりで一重だった。** しかも普段は一段目が通るので、
**壊れていることを知る機会が無い。**
（同じ形の話は [落ちないバグの見つけ方](/garden/silent-failures/)）

**使われない経路は、使われないまま腐る。** 二段目を持つなら、
**わざと一段目を止めて二段目だけで通す試験**を一度は通しておかないと、持っている意味がない。

## 未確定

- **上限の単位が分からない。** トークンなのか、金額なのか、推論トークンが
  重く数えられているのか。**48万〜58万の幅は、その差で説明がつく範囲にある**
- **窓が明けるとき、全部戻るのか少しずつ戻るのか確かめていない。**
  1回の枠切れしか観測していないので、ここは推測
- **窓が閉じた「後」いつまで無操作なら次が新しく開くのかも未確認。**
  上の表では窓の外の1回目を新しい窓の開始として扱ったが、**それが仕様だという確認は取れていない**
