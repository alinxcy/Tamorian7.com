12時30分、後処理が止まった。Google Drive の一覧が取れない、それだけだった。

今回困ったのは、録画のエンコード待ちを積むために Drive を見にいく後処理と、過去の録画を再生するために Drive をマウントしている rclone-archive.service の二つ。止まったのは前者だった。

実は、原因はそのどちらの側にもなかった。

12:02:32、`~/.config/rclone/rclone.conf` の所有者が root に変わっていた。パーミッションは 600。一般ユーザーからは `rclone lsf` すら通らなくなっていた。

書き換えたのは、毎時 root で走っている gdrive-backup だった。録画を Drive へ引っ越す、後処理とは別のジョブ。それが `RCLONE_CONFIG` に本人の rclone.conf をそのまま指定していた。rclone は OAuth のトークンを更新するたびに設定ファイルを書き直す。root で動いていたぶん、書き直した先も root 所有になった。

12:30 の後処理はここに引っかかって落ちた。Drive の一覧が取れないので、次に積むべきエンコードが分からない。

応急は昼のうちに入れた。後処理の Drive 確認を、rclone-archive.service がすでに立ち上げているマウントを scandir で読む方式に変える。設定ファイルを経由しないので、権限が壊れていても一覧は取れる。dry-run で次の番組が積めることを確認した。

ただしこの応急には、そのまま見過ごせない前提があった。マウントが「たまたま今上がっている」ことに寄りかかっていた。rclone-archive.service を再起動すれば、同じ設定ファイルを読めずにマウントも上がらなくなるはずだった（試してはいない）。そうなれば後処理だけでなく、過去分の再生も止まる。応急は延命であって、直してはいなかった。

直すには sudo が要った。17:38 に sudo で復旧。rclone.conf を本人所有に戻し、root 用には `/etc/rclone/gdrive-rec.conf` という別の複製を用意した。systemd の drop-in で root 側の `RCLONE_CONFIG` をそちらに差し替える。毎時の root 実行が本人の設定を書き換えない構成にした。ユーザー側の `rclone lsf` が戻ることも確認した。翌 9/17 の 03:02 の回まで毎時のジョブが走った後も、rclone.conf の所有者は本人のままだった。

設定ファイルを一つ共有していただけで、毎時のジョブが後処理と再生の足元を書き換えられる状態になっていた。
