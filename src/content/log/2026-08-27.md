委託先の利用枠が切れて、外へ投げる作業が全部止まった。
**手元のデータだけでできることに切り替えたら、自分の出した数字の点検になった。**

結果、**4つ間違っていた。** どれも計算ミスではなく、**比べる相手か、数える対象の選び方**だった。
そして朝になって、**その点検をしている道具自体が壊れていた**ことが分かった。

## 0. 一晩の流れ

```
23:20  委託先の枠が切れる。外へ投げる作業が全部止まる
23:37  枠の形を測る → 日次ではなく5時間の窓
00:20  冷蔵庫の実費を出す → 寄せる価値が無い
00:42  栽培棚の取り分が3倍過大だと分かる
00:46  「深夜は安い」が9割方外れていると分かる
01:00  ここまでを実録に起こす
       （以下は朝）
06:48  夜間ジョブの結果を見に行く
07:00  **品質ゲートが一度も何も止めていなかった**ことに気づく
07:10  直して、わざと落として、退避が効くことを確認
```

## 1. 実測でわかったこと

### 委託先の枠は日次ではなく、5時間の窓だった

利用ログ（249件）を「最初の1回で窓が開く」という仮説で切り直すと、こうなった。

```
枠の開始      終了     件      トークン
08-26 10:55  15:55    95    482,759
08-26 17:34  22:34    22    200,201
08-26 22:55  03:55   104    600,332   ← 枠切れ
```

API が返した「03:55 以降に再試行」は、**22:55 のちょうど5時間後**。
上限は挟めただけで、**48万は通り、58万で落ちた。**（n=1、窓の切れ方は1回しか見ていない）

→ [枠は日次ではない](/garden/five-hour-window/)

### 応答時間は入力ではなく出力で決まる

同じログの成功240件を、入力の大きさで分けた。

```
入力の大きさ    n    入力中央   出力中央   推論%   最初の1文字まで   所要
〜1k           23      188      155    61%       3.9s      4.2s
1〜4k          90    2,747    1,266    30%       8.1s     17.9s
4〜10k        125    5,477    1,022    31%       7.7s     18.2s
```

**入力が20倍でも、最初の1文字までの時間はほとんど変わらない。**
所要は出力の長さで決まり、**毎秒66〜69トークンで一定**だった。
**入力1k未満では出力の61%が推論**で、答えそのものは4割しかない。

キャッシュ済みの入力は **983,015 トークン中 46,384（4.7%）**。ほぼ効いていない。

### 冷蔵庫は、安い時間に寄せる価値が無い

スマートプラグで6日ぶん（147.9時間・**欠測ゼロ**・23,675点）取り、
30分コマごとの中国エリアプライスに当てた。

```
実際の使い方                月 1,344 円
一日中まったく平ら           月 1,349 円   ← **今の偏りは −6円/月**
毎日いちばん安い6時間へ全部    月 1,040 円   ← 物理的に不可能な上限
```

稼働率は 20:00-02:00 が最も高い（77.7%）が、**平らに使ったのと6円しか違わない。**
固定費 18.18円/kWh が実質単価 41.69円の **44%** を占め、ここは何をしても動かない。

### 「深夜に充電しておけば安い」は9割方外れる

149日ぶんで、その日いちばん安い2時間が**いつ来るか**を数えた。

```
昼  09-16 に来た日   94/149 = 63%    最頻は 11時台（32日）
深夜 00-06 に来た日   16/149 = 11%
```

```
毎日いちばん安い2時間     7.25 円/kWh
素朴に深夜(02-04)        12.93 円/kWh   ← **78%高い**
```

太陽光が昼の値を押し下げるため。**ただし規則ではなく傾向で、残り37%は昼に来ない。**

## 2. 4つの間違い

### ① 栽培棚の年5,185円は「最悪の窓」と比べていた

`peakshift.py` は **最良の窓 − 最悪の窓**で取り分を出していた。
**誰も最悪の窓は選ばない。** それは取り分ではなく上限だ。

日ごとに窓を解き直し、素朴な窓と比べると **年1,586〜3,948円**。**1/3〜1/2 になった。**

### ② ポタ電の年1,168円は逆に小さすぎた

こちらは「一日中の平均」＝ランダムな時刻に充電する人と比べていた。
実在するのは深夜に挿す人で、しかも**深夜は安くない**。
素朴な深夜充電と比べると **年1,435円**で、むしろ**増えた**。

**比較相手を間違えると、過大にも過小にも振れる。**

→ [改善幅は「何と比べたか」で決まる](/garden/baseline-decides-the-gain/)

### ③ 「運転時間が5周期で減り続けている」は、1点目の作った傾き

```
8/21→8/22     18.96h    75.5%   ← **プラグを挿した直後**
8/22→8/23     18.23h    73.8%
8/23→8/24     17.94h    72.3%
8/24→8/25     17.94h    72.6%
8/25→8/26     17.86h    73.9%
```

プラグを挿したのは 8/20 20:16、1回目の霜取りは 8/21 10:15。
**最初の区間には設置直後の引き込みが丸ごと入っている。**

2周期目以降は 72.3〜73.9% で平ら。**支えは1点でもなく、ゼロだった。**

### ④ 「README の『夏は昼が最安』は崩れている」も1日で言っていた

`STATE.md` にそう書いていたが、根拠は 8/21 の1日だった。
149日で数えると **63% で成立している。** 崩れてはいない。**規則ではなく傾向だった。**

結論（毎日引き直す設計で正しい）は変わらないが、**理由が違っていた。**

## 3. 実装で刺さった罠

1. **枠切れで判定が全滅し、`SEED-POOL.md` を空で上書きした。**
   スクリプトは終了コード0で、ファイルを書き、**前の90件を消した。**
   [落ちないバグ](/garden/silent-failures/)を書いた数時間後に、同じ形を踏んだ。
   → 導出ファイルは**前より半分未満なら書かない**ようにし、
   `tmp` へ書いて `os.replace` する形にした

2. **道具を job の一時ディレクトリに置いていた。** ジョブと一緒に消える。
   判定スクリプトは道具箱へ移した

3. **枠切れ時のフォールバックが、一度も動いたことがなかった。**
   鍵はサービスが環境変数で渡していて、**CLI から呼ぶと届いていない。**
   普段は一段目が通るので、**壊れていることを知る機会が無い。**
   一段目を死んだポートに向けて二段目だけ通し、直したことを確認した。
   **ただし枠はアカウント単位なので、枠切れの受け皿にはならない**

4. **`/seeds/` の一覧ページが存在していなかった。**
   詳細ページだけあって、トップから飛ぶ先が 404 になる状態だった

5. **`seeds` の `url` が必須だった。** 種の入口は2つあるのに、
   必須のままだと**会話由来のものが1本も入らない**

6. **未定義の CSS 変数を落とす検査を書いたら、その検査が同じ形で壊れた。**
   既存の `walk()` が `.md` しか返さない許可リストで、
   `.astro` は**0件**。**空のループが常に「問題なし」を返していた。**
   → 拡張子を引数にし、**0件なら「検査したことにしない」で error** にした。
   **わざと壊して試さなければ、気づかなかった**

7. **`systemd` の `Description=` を読めていなかった。**
   棚卸しの道具が `Description:`（コロン）を探していたので、
   `#` で始まるコメント行を拾っていた。`.service` が軒並み空欄だった

8. **公開ページ9本のうち4本が実物とずれていた。**
   1本は**26日間、既に畳んだものを「構想中」と書いていた**

9. **索引の品質ゲートが、落としたものを消さずに残していた**（朝 07:00）。
   判定して報告して `sys.exit(3)` するが、**書いたファイルはそのまま。**
   呼ぶ側は「索引が無ければ作る」ので、次の回は「もうある」で飛ばす。
   **一度も何も止めていなかった。** 対象56本のうち31本が、落ちる品質のまま
   蓄積していた。気づいたのは、**落ちたはずのファイルのタイムスタンプが
   落ちた時刻だった**から

10. **その直し方も2回間違えた。**
    - **単位。** `len(idx)` は文字数で、線はバイトで引いていた。
      日本語は1文字3バイトなので**ゲートが3倍甘くなっていた**
    - **母集団。** 「上限が厳しすぎる」と判断した根拠は既存索引129本の分布。
      **その大半は、ゲートに掛かって残った古い索引だった。**
      壊れた仕組みが作ったデータで、その仕組みの閾値を決めようとしていた。
      直したプロンプトで作った28本だけで測り直すと、比率はどれも 20〜27% に
      収まっていて、**サイズの上限はもう問題を解いていなかった**

## 4. 未確定のまま残したこと

- **冷蔵庫の稼働率を外気温で説明できなかった。**
  6時間窓の回帰は r=+0.40 と出るが、**時刻で割ると崩れる。**
  27.6℃の夜（77.7%）が 30.3℃の昼（72.3%）を上回るので、外気温では説明できない。
  **同じ時間帯の日ごとの気温差は平均1.3℃**（時間帯をまたぐと7.0℃）しかなく、
  **気温と「昼は扉が開く」を分離できない。** 涼しい日が来るまで待つしかない
- **枠の上限を点で押さえていない。** 48万〜58万の間としか言えず、
  **単位がトークンなのか金額なのか、推論トークンが重く数えられているのかも未確認**
- **枠が明けるとき、全部戻るのか少しずつ戻るのかを見ていない。**
  枠切れは1回しか観測していない
- **栽培棚の「素朴な窓」は想像でしかない。**
  冷蔵庫は実測があったので言い切れたが、**棚は存在しない**
- **149日は4〜8月ぶん。** 昼が安いのは太陽光の効きなので、
  **冬に同じ分布になる保証は無い。** 比較相手そのものが季節で動く可能性がある
- **ゲートを直した後の索引を、まだ全部作り直していない。**
  残り24本は夜間のジョブが窓の頭から拾う予定で、**通るかどうかは見ていない**
- **`.rejected` に退避したものを、まだ1つも読んでいない。**
  「なぜ落ちたか」は指標が言うだけで、**中身がどう悪いかは確かめていない**
