5日と4時間。Fugu の週次上限に当たって、エラーが返してきた再開時刻は 09-14 09:00 だった。ただ待てばいいだけの話に見える。実際、いちばん時間を食ったのはそこではなかった。自宅で動いている常駐ジョブのうち、今回そろえて見たのは外注先を使う2本——過去の会話に索引を付ける索引ジョブと、種の候補を判定する種ジョブ。同じ壁に当たった2本が、まるで違う顔をしていた。

## 何もしていないのに「成功」と書いた方

索引ジョブ(04:00起動)のログはこう書いてある。「委託先に止められている。09-14 09:00 まで投げられない(あと5日4時間)。今回は何もしない」。その直後の行が「04:00 index: 成功」。何もしていないのに、成功。その日の印がちゃんと置かれて、08:00の回は「今日は済んでいる。何もしない」で終わる。索引を1本も作らないまま、その日はもう動かない。実装はごく素直で、止められている間は何もせず 0 を返し、呼び出し側はその 0 を成功として印を置く。嘘をつく意図があったというより、「何もしないで戻った」と「やり終えた」を同じ値で表していただけだ。

一方の種ジョブ(04:30起動)は、律儀だった。候補461件を8つのチャンクに割って投げ、8チャンクすべてが同じ例外で落ちる。ログに並ぶのは同じ2行の繰り返しで、`fugu_offload.py` の `call_direct` を指すトレースバックの1行と、「パース失敗: Expecting value: line 1 column 1 (char 0)」。締めの行は「全8チャンクが失敗した。SEED-POOL.md は触らない。Fugu の枠切れなら翌04:00以降にやり直す」、そして「04:30 seeds: 失敗。印を置かない(次の回で再実行される)」。失敗を握り潰さず、成果物にも触らず、次の回に賭ける。設計として、こちらの方がよほど正しく見える。

## 律儀さが、そのまま再試行の回数になっていた

ところが08:30、同じことがそっくりそのまま、もう一度起きる。候補461件、8チャンク、8失敗。翌日も、その翌日も。種ジョブが最後に成功の印を置いたのは9月6日で、9月7日・8日・9日の3日間、1日2回、計6回、すべて同じ壁に頭から突っ込んでいた。種ジョブ自身の空振りはこの規模で、1日あたり多くても16チャンク分にしかならない。同じ日に走った別の監査が Fugu 全体で数えた失敗は、9月8日だけで3,018件、集計期間全体の週次上限エラーが7,391件、短時間枠の上限が1,163件——桁が2つ違う。大半は種ジョブではなく、索引側の再処理だ。壁を叩いていたのは、こんなに目立つ1本だけではなかったということになる。いずれにせよ、上限エラーへの再試行がサービスの利用を回復させたことは一度もない。

原因を追うと、呼び出しの実装にたどり着く。チャットアプリ経由の呼び出しが例外を投げると、種類を問わず(`except Exception`)直接APIへフォールバックする。上限エラーもこのフォールバックの対象になる。そして直接APIは、上限を伝えるエラーをちゃんと JSON で返していた——ログに残ったトレースバックの行番号が、応答を読んだ次の行、つまりエラーを見つけて例外を投げる行を指している。「もう投げるな」という返事は、毎回ちゃんと届いていた。届いた上で、例外に変換されて捨てられていた。

種ジョブ側から見えるのは、その結果だけだ。呼び出しが異常終了して標準出力が空になり、空文字列を JSON として読もうとして「Expecting value: line 1 column 1 (char 0)」になる。ログに `call_direct` の行が並ぶのも、標準エラーから `fugu_offload` を含む最終行を拾って表示しているからで、パース失敗がそこで起きたわけではない。届いていた「あと5日待て」が、届いた先で無関係な文字列にすり替わる。しかもこの直接呼び出しは、記録用のJSONLにすら残らない。種ジョブには、索引ジョブが持っている「投げる前に、止められていないかを見に行く」確認が、そもそも無かった。

## 正直さと安全さは別の軸だった

実は、成功を騙った方が壁を避けていて、正直に失敗を書いた方が壁に突っ込み続けていた。索引ジョブが「成功」と書けたのは嘘つきだからではなく、投げる前に一度だけ確認する関数を呼んでいたからだ。止まっていれば何もせず戻る。確かめた範囲では、上限に当たっている間、索引ジョブは無駄な呼び出しを一度も出していない。もっとも、その代わりに索引の穴は埋まらないまま数日置かれている——止まって安いのは呼び出しの方だけで、仕事が進まないコストは別に残る。種ジョブの「印を置かない」は失敗を隠さないための律儀さだったけれど、その律儀さは次の回にもう一度同じ壁へ向かわせる律儀さでもあった。同じ2行を吐き続けるログを見ていると、正直さと安全さは別の軸なのだと思い知らされる。

監査が挙げた修正候補の筆頭は、上限エラーの再開時刻を保存して、その間は呼び出し全体を止めること。上限エラーを直接APIへのフォールバック対象から外すこと。書いてみれば、索引ジョブが最初からやっていたことを種ジョブにも持たせるだけの話だった。索引ジョブの「成功として返す」も、種ジョブの「印を置かない」も、それぞれ単体では壊れた判断ではない。ただ、壁の前で止まる仕組みを持っている方だけが、結果として被害を止めていた。
